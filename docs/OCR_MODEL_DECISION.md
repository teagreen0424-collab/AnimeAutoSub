# AnimeAutoSub · 硬字幕 OCR 文本识别模型决策记录 (OCR_MODEL_DECISION.md)

> **生效日期**: 2026-11-01  
> **文档状态**: 冻结生效 (依据 PO L0–L5 指令收口)  
> **核心原则**: 生产环境强制绑定默认 `PP-OCRv6` 多语种识别模型，严禁因字面配置误切 `japan` 专用模型。

---

## 1. 候选模型对比

在开发过程中，曾对 RapidOCR 官方提供的两套识别模型进行了完整对照验证：

| 模型标识 | 权重文件名 | 词表规模 | 模型架构与来源 |
| :--- | :--- | :--- | :--- |
| **候选 A: Multi 多语种模型 (当前生产)** | `PP-OCRv6_rec_small.onnx` | 18,710 字符 | RapidOCR 默认 PP-OCRv6 紧凑型多语种模型 |
| **候选 B: Japan 专用模型** | `japan_PP-OCRv4_rec_mobile.onnx` | 4,401 字符 | PP-OCRv4 日语专用移动端模型 (`japan_dict.txt`) |

---

## 2. 真实素材实测数据

在 `bench/truth_frames/`（12 帧长集，真值 317 字符）上进行的严格实测对照数据如下：

| 指标 | 候选 A (PP-OCRv6 Multi 默认) | 候选 B (japan_PP-OCRv4 Mobile 专用) | 差异 (A vs B) |
| :--- | :--- | :--- | :--- |
| **编辑距离 (总)** | **53 处** | 87 处 | **A 减少 34 处** |
| **字符错误率 (CER)** | **16.72%** (P2优化后 13.25%) | **27.44%** | **A 优 10.72 ~ 14.19 pt** |
| **完全正确帧数** | 2 / 12 帧 | 0 / 12 帧 | A 显著占优 |
| **推理速度 (稳态)** | ~195 ms / 帧 | ~210 ms / 帧 | 基本相当 |

---

## 3. 决策结论

**结论：生产环境必须且只能使用 候选 A (`PP-OCRv6_rec_small.onnx`)。**

- **为何看起来是“反常识”的**：
  直觉上开发者常认为“日语字幕应当使用专门的日语模型（japan）”。然而在实际动漫/影视硬字幕场景下，`japan_PP-OCRv4_rec_mobile` 因参数量受限、泛化能力弱，对于艺术字体、带描边字幕以及复杂背景干扰的抗噪能力远逊于迭代更先进的 `PP-OCRv6` 架构。
- **为何严禁回退**：
  将识别模型切换为 `japan_PP-OCRv4` 会导致全片字幕识别 CER 直接从 **13%~15% 断崖式恶化至 27.44%**，造成灾难性降级。

---

## 4. 生产配置与测试契约防呆防误

为了避免后继维护者因配置名产生歧义而“误修”生产代码，特建立如下双重工程防护：

1. **生产代码显式配置 (`pipeline_ocr.py`)**：
   ```python
   # 刻意使用默认 PP-OCRv6 多语种模型。
   # 实测：PP-OCRv6 multi CER 16.72%；japan_PP-OCRv4_rec_mobile CER 27.44%（更差）。
   # 不要"修正"成 japan 专用模型，会掉 10 个百分点。详见 docs/OCR_MODEL_DECISION.md。
   ocr_params = {}
   ```
2. **测试硬契约防护 (`tests/test_ocr_model_contract.py`)**：
   直接从 `pipeline_ocr.py` 导入 `build_ocr_engine()`，硬断言：
   - 实际加载的模型文件名必须为 `pp-ocrv6_rec_small.onnx`；
   - 实际词表大小必须为 `18710`。
   若任何人试图在生产中将模型改回 `japan_PP-OCRv4`，单测将立即 FAIL 阻断集成。
